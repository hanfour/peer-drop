## 0. 提案檢查清單（`product-goals.md` §6.1）

1. **支柱**：慢（紙條仍是一次一張）、私（綁定在本地加密連線內完成，平台看不到誰遇見誰）。
2. **原則**：
   - 原則 1（私密優先）：交換過程不經伺服器；唯一的新增伺服器流量是「查對方帳號的公開目錄」，與日後寄紙條時本來就會發生的查詢相同，伺服器仍不保存關係（目錄查詢只留每分鐘計數）。
   - 原則 2（慢優先）：紙條氣泡**沒有已送達／已讀**，不新增即時狀態。
   - 原則 3（圈內優先）：只有面對面（同一個本地連線）才能綁定，不做推薦、不做搜尋。
3. **非目標**：不碰「陌生人社交」——沒有雙方按下就不給任何帳號資訊，且第一版**不做盲發**（使用者已決定）。
4. **推動指標**：輔助指標中的「首次紙條互動」（讓線下相遇的人能無縫轉為遠端紙條）。

## 1. 意圖

使用者描述的情境：在圖書館與不認識的同學藉藍牙／Wi-Fi 聊天，對方走遠後想問「下週還來嗎」。目前對方一離開，輸入框就停用，這段緣分就斷了。專案 C 讓兩個人在**雙方明確同意**時，把這個「裝置朋友」綁定到彼此的「紙條帳號」，之後對話在同一個串裡：在線時即時聊天，下線時改寫紙條。

## 2. 目標、非目標、反目標

### 目標
1. 在本地加密連線內，提供「交換紙條」：**雙方都按下**才交換紙條帳號資訊。
2. 綁定後，該朋友寄來的**簽名紙條**與我寄給他的紙條，出現在同一個對話串。
3. 對方下線且已綁定：輸入框開啟、紙條樣式、可寄出文字紙條；未綁定：維持目前的鎖定與誠實提示。
4. 舊版 App 的連線不會被破壞。

### 非目標（第一版）
- **盲發／投石問路**（使用者決定不做）。
- 「時空紀念冊」、把相遇存檔：另案。
- 把同一個人的 iPhone 與 Mac 視為同一位朋友（現有架構一台裝置一個帳號；綁定是「裝置對帳號」）。
- 紙條的已送達／已讀、編輯、回覆、表情、圖片檔案語音（紙條系統本身限制）。
- 以帳號 ID 加沒見過面的朋友為對話串（手動輸入 ID 寄紙條維持現狀，仍走紙條信箱與「已寄出」）。
- 把紙條解密搬離主執行緒、換機還原。

### 反目標（做出來卻算失敗）
以下是我的推測，不是使用者說的：
- 任何一方在對方未同意時，就取得對方的帳號資訊。
- 綁定到錯的帳號（被冒名或被中間人換掉），使用者把紙條寄給別人。
- 舊版 App 一遇到新訊息就斷線。
- 一個動作讓使用者以為還能即時聊，其實是寫紙條（模式必須一眼看出來）。
- 紙條寄失敗卻悄悄消失。

## 3. 使用者已決定的事

1. 必須「雙方都按下才交換」，在按下之前**不得傳送任何真實帳號資訊**。
2. 沒完成交換、對方走遠：輸入框鎖定並解釋原因，對話紀錄保留在本機。
3. 完成交換、對方走遠：輸入框保持開啟，畫面為紙感，可遠端寄紙條。
4. 第一版**不做盲發**。
5. 同意修改產品目標 §1.3／§4.1（已改）。

## 4. 設計

### 4.1 交換協定（承載在既有的本地加密通道）

- **能力宣告**：在 HELLO 的 `PeerIdentity` 加一個欄位 `supportsNotesExchange`（`decodeIfPresent ?? false`，與 `supportsSecureChannel` 同模式）。**只有雙方都宣告才會送出交換訊息**，否則舊版會因為不認得的訊息型別而斷線（已由讀碼確認：未知型別使解碼失敗並使連線進入 `.failed`）。
- **單一新訊息型別** `notesExchange`，payload 含 `phase`：
  - `intent`：「我想交換」，**不含任何帳號資訊**。
  - `reveal`：`{accountId, signingKey}`（暱稱不傳，改由目錄結果顯示，避免對方自稱）。
  - `cancel`：撤回意願。
- **流程（先承諾、後揭露）**：
  1. 我按下「交換紙條」→ 跳確認「將把你的紙條帳號分享給 X」→ 本機 `myIntent = true`，送 `intent`。
  2. 收到對方 `intent` → `peerIntent = true`，聊天畫面顯示「X 想和你交換紙條」（可按下同意，等同第 1 步）。
  3. **當 `myIntent && peerIntent`**：雙方各送 `reveal`。
  4. 收到 `reveal` 且**我方已有 `myIntent`**（沒有就忽略，防止未經同意的主動推送）：進入驗證（§4.2）。
  5. 驗證成功 → 寫入綁定。
- **同一次連線內有效**：斷線時所有 `intent`／`reveal` 狀態清空，不留待處理、不事後補送。
- **一方沒按**：畫面顯示「等待對方也按下交換」，不洩漏任何資訊；對方走遠即作廢。
- **對方版本過舊**：按鈕為停用狀態，說明「對方的 App 需要更新才能交換紙條」。
- **安全要求**：僅在 `secureChannelState == .secured` 且 `pinningVerdict != mismatch` 時允許；`fallbackPlaintext` 一律拒絕。重複的 `intent` 忽略；payload 大小與欄位長度設上限。
- **協定版本**維持 v1，不做版本協商（現有也沒有），靠能力旗標與跨版本迴路測試保證相容。

### 4.2 驗證與綁定

- 收到 `reveal` 後，查 `GET /v3/directory/<accountId>`（**不帶 bundle**，不消耗對方的一次性預備金鑰）。
- **接受條件**：目錄回傳的 `identityKey` 等於本地連線釘住的對方身分公鑰（`TrustedContact.identityPublicKey`，同一把鑰匙同時是帳號與連線身分），且 `signingKey` 與 `reveal` 一致。任一不符 → 不綁定，顯示「無法驗證對方的紙條帳號」。
- **離線無法查**：記為「待驗證」，在 App 回到前景或有網路時重試；**驗證成功前，該朋友的紙條不進對話串**、輸入框不開啟離線紙條。
- **儲存**：寫入現有但從未被寫入的 `TrustedContact.accountId`，並新增 `TrustedContactStore.find(byAccountId:)`。
- **裝置朋友 ↔ 聯絡人**的對應用一個集中函式（`FriendBinding.contact(for: DeviceRecord)`），依序嘗試 `record.id`、`record.peerDeviceId`、連線中的身分，避免各處各自比對。
- **金鑰變更**（對方重裝）：既有的金鑰變更警示觸發時，**清除該聯絡人的 `accountId` 綁定**，需重新交換（寧可嚴格，避免寄給舊帳號）。
- **取消綁定**：朋友詳情提供「取消紙條綁定」；既有紙條保留在紙條信箱／已寄出，只是不再屬於該對話串。
- 綁定是**單向可成立**：若 reveal 傳送中斷，一方可能已綁定、另一方尚未；未綁定那方維持鎖定，下次連線再按一次即可。

### 4.3 對話串合併（渲染層，不改儲存格式）

- 資料仍分兩處（聊天訊息在 `ChatManager`，紙條在 `NotesStore`）；對話串**在顯示時合併**。
- 歸屬規則：
  - 收到的紙條：寄件人狀態為 `verified` 且其 `accountId` 等於該聯絡人的 `accountId`。
  - 寄出的紙條：`recipientAccountId` 等於該 `accountId`。
  - 匿名、未驗證、無法解密、來自未綁定帳號的紙條**維持在紙條信箱**。
- 顯示：沿用聊天氣泡元件，紙條使用 A＋B 已定義的 `note` 氣泡樣式（淡黃填色、虛線邊、狀態「📮 已寄出」）。**沒有**已送達、已讀。紙條氣泡不提供回覆、編輯、表情；長按只有複製與本機刪除。
- 排序：收到的紙條用**伺服器收件時間**（`receivedAt`），寄出的紙條用本機寄出時間，避免對方時鐘偏差；聊天訊息用自身時間戳。
- 對話清單（紙條分頁）：最後一則與時間要納入紙條；未讀數 = 聊天未讀 + 該帳號的紙條未讀；開啟對話串時標記該帳號紙條已讀（`NotesStore.markRead` 會同步伺服器，這與現在行為相同）。

### 4.4 寄信（輸入框模式）

純函式 `ThreadTransport.decide(presence:, binding:, account:)`：

| 對方狀態 | 綁定 | 我方帳號 | 結果 |
|---|---|---|---|
| 在線 | 任意 | 任意 | `live`（照目前行為）；未綁定且對方支援時顯示「交換紙條」按鈕 |
| 附近／下線 | 已驗證 | `ready` | `note`：紙感底、輸入框開啟、傳送鈕為紙條樣式 |
| 附近／下線 | 已驗證 | 非 `ready`（離線、不支援） | 輸入框開啟但提示「有網路時才能寄出」，進入本機待寄佇列 |
| 附近／下線 | 未綁定或待驗證 | — | `locked`：目前的誠實提示，並附「雙方交換紙條後才能離線聯絡」 |

- **模式切換必須看得見**：連線在輸入中途斷掉時，**不自動改寄紙條**；文字保留在輸入框，畫面切換為紙感並提示「已改為紙條」，使用者再按傳送才寄。
- 紙條限制在輸入框顯示：2,000 字元上限，接近時顯示計數。
- **待寄佇列（我的判斷）**：目前紙條寄失敗會直接丟出錯誤且不留存。對話串裡這會讓字消失，所以新增一個**本機加密的小型待寄清單**（純新增，不動既有 `NoteRecord` 格式）：狀態 `queued／failed`，App 回前景與連線恢復時重試，失敗的氣泡顯示「未寄出，點此重試」。
- 每次寄紙條仍會向目錄取一份預備金鑰包（消耗對方一把一次性金鑰）並做工作量證明——與現行相同，不做額外處理。
- 推播：沿用既有紙條推播；點開時若寄件人已綁定，開啟對話串，否則開紙條信箱（現有 `.openNote` 的判斷邏輯擴充）。

### 4.5 UI 位置

- 聊天畫面右上（iOS 與 Mac 聊天視窗）：**「交換紙條」**按鈕，三態：未綁定（可按）、等待對方（已按下）、已綁定（顯示郵戳徽章，點擊可取消綁定）。
- 對方頭像／朋友列：已綁定者顯示小信封徽章（與 A＋B 的「下線徽章」區分：此為「可寄紙條」標記，不是下線）。
- 主頁、紙條分頁：不變，除了紙條分頁的預覽與未讀納入紙條。

## 5. 約束與風險

- 不改既有儲存格式與既有訊息；新增：HELLO 一個可選欄位、一種訊息型別、`TrustedContact.accountId` 的寫入、待寄佇列。
- **協定相容**：必須做跨版本迴路測試（App Store 版 ↔ 新版，以真實 `ConnectionManager` 在本機多程序），確認新版不對舊版送新訊息、舊版連線不受影響（專案既有做法）。
- 一台裝置一個帳號：iPhone 與 Mac 是兩位朋友。
- 帳號可能永遠不存在（不支援證明或離線註冊失敗）：該朋友顯示「對方尚未開通紙條」，交換按鈕停用並說明。
- 未驗證 SAS 的首次連線也允許交換（使用者情境是陌生同學，強制比對安全碼會讓流程無法使用）；代價是首次連線時遇到中間人，會綁定到攻擊者自己的帳號。這與對該人聊天的信任程度相同，**不比即時聊天更糟**，但需在 UI 文案中避免暗示「已驗證身分」。
- 伺服器端不需要新增 API；新增流量僅為對方帳號的目錄查詢。
- 主執行緒負擔：紙條摘要與合併需沿用專案 A＋B 的做法（快取、不在 `body` 內逐列解密）；移出主執行緒另案。

## 6. 驗證

- 單元：交換狀態機（intent／reveal／cancel／斷線清空／未 intent 即收 reveal 被忽略／重複 intent）、驗證邏輯（公鑰相符／不符／離線待驗證）、`ThreadTransport.decide` 全表、合併排序與歸屬規則（含匿名／未驗證／無法解密）、待寄佇列重試。
- 整合：本機兩個真實 `ConnectionManager` 迴路測試完整交換；跨版本測試（舊版不被破壞）。
- 畫面：下線已綁定／未綁定、等待對方、紙條氣泡、模式切換；淺色夜間、最大字級。
- 實機（使用者）：真實藍牙／Wi-Fi 連線中按交換、斷線後寄紙條並在另一台收到。

## 7. 與產品目標的差異

- §1.3／§4.1 已依使用者核可修改（見 `product-goals.md` 變更紀錄）。
- §4.2「圈內＝P2P 信任聯絡人」：本專案的綁定正好提供其中一半的資料，但**不實作**陌生人匣分流（另案）。

## 8. 我的判斷（請核可時檢查）

1. 先承諾後揭露（intent → reveal），避免單方洩漏。
2. 揭露只含 `accountId`＋`signingKey`；暱稱一律取自目錄。
3. 交換狀態不跨連線保存。
4. 金鑰變更即清除綁定。
5. 允許 `.unknown` 信任等級的首次連線交換（不強制 SAS），文案不暗示已驗證。
6. 待驗證期間紙條不進對話串。
7. 模式切換不自動改寄。
8. 新增本機待寄佇列（純新增）。
9. 收到的紙條以伺服器收件時間排序。
10. 單向綁定可存在，由下次連線補齊。

## 10. 建置者檢查後補充的決定（我的判斷，非使用者所說）

一位沒看過脈絡的資安取向建置者讀過文件並對照程式碼後，指出下列問題。我逐一決定如下；其中 10.1–10.3 修正了 §4.1／§4.2 的原寫法，**以本節為準**。

### 10.1 驗證要比對的鑰匙（硬性守門條件）
現況的釘選判定用的是 HELLO 裡**自稱**的身分公鑰，沒有確認它就是加密通道握手實際用的那把鑰匙。因此交換與綁定**必須同時滿足**：
1. 握手實際使用的對方身分公鑰 ＝ HELLO 自稱的公鑰 ＝ 本機釘選的 `TrustedContact` 公鑰（沿用既有 `handshakePeerIdentityKey` 的比對，不得省略）；
2. `pinningVerdict != mismatch`；
3. 目錄回傳的 `identityKey` ＝ 上述公鑰；
4. `reveal` 內附一個 **`signingKey` 的簽章**，簽的是「`accountId` ‖ 雙方握手身分公鑰（固定順序）‖ 本次連線隨機值」，證明揭露者同時持有該帳號的簽章金鑰，且簽章綁定了這次連線，無法重放到別的連線或別的對象。
任一不符就不綁定。

### 10.2 為什麼這樣夠，以及已知殘餘風險
目錄的 `identityKey` 本身不能證明「帳號屬於持有這把鑰匙的人」：伺服器註冊只驗證簽章金鑰，不驗證 X25519 私鑰持有，且 `identity_key` 先到先得，攻擊者可搶註尚未註冊的別人的公鑰。有了 10.1，揭露者必須**同時**持有該連線身分的私鑰（握手證明）與帳號簽章金鑰（簽章），冒名的空間只剩「本人串通」。搶註導致他人日後註冊被擋（409）是**既有的伺服器問題，本專案不修**，列入待辦。

### 10.3 交換訊息只收「信封內」的
`notesExchange` 必須是從加密信封解出來的才處理；明文（通道建立前、legacy 明文、被注入）一律丟棄，不更新任何狀態、不顯示任何提示。實作上要在訊息分派層帶一個「來自信封」的旗標。

### 10.4 只限本地直連
僅在**本地直連（區域網路、藍牙、手動 IP）**允許交換；**中繼（邀請碼／WebRTC）連線不允許**，且在中繼連線上不宣告能力旗標。理由是產品定位為「面對面」。

### 10.5 對方沒有帳號怎麼知道
- 按鈕對雙方都支援的連線**一律可按**（不預先洩漏對方有沒有帳號）。
- 雙方 `intent` 都到齊後，若某方帳號不可用（`AccountManager` 非 `ready`），該方送 `reveal` 的替代：phase `unavailable`（不含任何帳號資訊）。收到的一方顯示「對方尚未開通紙條帳號」，交換結束。
- 設計 §5 的「交換按鈕停用並說明」改為：只在**對方 App 過舊**時停用；「尚未開通」是雙方按下後才得知。

### 10.6 綁定的唯一性與對應
- **綁定掛在 `TrustedContact`（以連線的握手身分鑰匙為準）**，不是掛在 `DeviceRecord`；`DeviceRecord` 只透過集中函式對應到聯絡人。
- **`accountId` 在所有聯絡人之間唯一**：新綁定成立時，清除其他聯絡人身上相同的 `accountId`。
- 對應不明確時（同名合併、多筆候選）**拒絕綁定並提示**，不猜。
- 重裝：現況重裝後 `PeerIdentity.id` 會重生並建立新聯絡人、不觸發金鑰變更警示，舊聯絡人的綁定會殘留。這靠上一條的唯一性規則收斂（重新交換時舊的被清掉）；§8.4「金鑰變更即清除綁定」只涵蓋有警示的情況，不再宣稱涵蓋重裝。

### 10.7 待驗證要跨連線保存（修正 §4.2 與 §8.3 的矛盾）
- 交換的 `intent`／`reveal` 狀態仍**只存在於該次連線**。
- 但驗證通過的前一步——「已收到合法 `reveal`、尚未能查目錄」——要保存為 `TrustedContact` 的**待驗證綁定**（加密儲存）：`{accountId, signingKey, 握手公鑰雜湊}`。理由：圖書館的 Wi-Fi 可能不通外網，不能因為當下查不到目錄就讓這次相遇白費。
- 重試時若目錄的 `identityKey` 與釘選不符或帳號不存在 → 判定失敗並清除，需重新交換。
- 待驗證期間：該朋友的紙條不進對話串、輸入框仍鎖定，並顯示「正在確認對方的紙條帳號」。

### 10.8 狀態機細節
- `reveal` 送出後，`cancel` 不影響已成立的綁定（要解除請用「取消紙條綁定」）。
- `intent` **10 分鐘逾時**（本機計時，逾時自動撤回並更新畫面）；按下前的確認文案寫明「若 X 也同意，將分享你的紙條帳號」。
- 「連線結束」＝ `PeerConnection` 進入 `.disconnected`／`.failed` 或被移除；短暫的傳輸層替換若不改變 `PeerConnection` 實例則視為同一次連線。
- 每方每次連線只送一次 `reveal`；未知的 `phase` 值要忽略而不拋錯（CM 端以 `try?` 解碼）。

### 10.9 已併入對話串的紙條與信箱
- 已綁定且驗證通過的朋友的紙條，**不再出現在紙條信箱列表**（去重），未讀只算一次（信箱的未讀徽章與分頁徽章要扣掉已歸入對話串的）。
- 紙條氣泡的刪除＝既有 `NotesStore.delete` 的行為（本機與伺服器一併刪），選單文字寫明「刪除這張紙條」，不再稱「本機刪除」。
- 紙條氣泡長按選單提供「封鎖」與「檢舉」，沿用以紙條 ID 呼叫的既有 API。

### 10.10 待寄佇列語意
- 接受極少數情況下「伺服器已收到但回應遺失」造成的重複紙條（沒有冪等鍵）。
- 自動重試最多 **3 次**（指數退避），之後轉為 `failed`，由使用者手動重試；排隊超過 **24 小時** 轉 `failed`。
- 簽章的 `sentAt` 用**實際寄出的時間**。
- 排隊期間綁定被清除（金鑰變更、取消綁定、被新綁定取代）：佇列項目轉為 `failed` 並標示「綁定已取消」，保留給使用者決定，不自動寄、不自動刪。
- 「回前景自動重試」是完成使用者**已按下傳送**的動作，與「不自動改寄」不衝突；但**不會**把一段留在輸入框、尚未按傳送的文字自動寄出。

### 10.11 ChatView 合併範圍
- 紙條只顯示時間戳**不早於目前已載入的最舊聊天訊息**者；「載入更早」時，同步把更早的紙條納入。
- **第一版搜尋不涵蓋紙條**。
- 切換成紙條模式時，正在回覆的狀態（`replyingToMessage`）一併清除。
- 紙條氣泡必須關閉：反應、編輯、對雙方刪除、回覆、滑動回覆、已讀勾勾。
- **「鎖定」與「可寄紙條」兩種紙感畫面要看得出差別**：可寄紙條時輸入框開啟、提示字「寫一張紙條給 X…」、傳送鈕為紙條樣式；鎖定時輸入框為灰色橫條。兩者都有 VoiceOver 文字，不靠顏色單獨表達。
- 目前 `inputBar` 寫死 `.disabled(!isPeerConnected)`，需改為由 `ThreadTransport.decide` 決定。

### 10.12 新增的測試要求
- 狀態機：同時按下、單方按下、重放舊 `intent`／`reveal`、逾時、未 `intent` 先收 `reveal`、明文注入、`unavailable`。
- 驗證：四鑰相等的每個不符分支、簽章綁定連線（跨連線重放失敗）、唯一性、待驗證到期與重試。
- 相容：新版對舊版不送新訊息；舊版 HELLO 不含旗標時按鈕停用；中繼連線不宣告旗標。

### 10.13 與使用者 §3 決定的關係
以上全部是為了落實使用者的決定 1（未同意不得傳送帳號資訊）與 4（不做盲發），沒有改變任何使用者已決定的事。**唯一偏離最初敘述的一點**是 10.5：「對方尚未開通」要等雙方按下後才會知道，而不是在按下前就能看到。
