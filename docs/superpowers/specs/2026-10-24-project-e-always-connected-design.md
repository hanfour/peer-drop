## 0. 提案檢查清單（`product-goals.md` §6.1）

1. **支柱**：私（伺服器不知道誰是誰的朋友、看不到內容）、慢（對方沒開 App 時自動退成紙條，不新增推播關聯）。
2. **原則**：
   - 原則 1（私密優先）：碰面代號是只有兩人算得出的暗號，伺服器看不出誰是誰；**殘餘風險**（IP＋時間的共現）已由使用者接受，見 §6.1。
   - 原則 2（慢優先）：「預設不做在線狀態」——本專案的在線狀態是**逐人、雙方同意、預設關閉**，且不提供「正在輸入」之外的新即時訊號；**需使用者核可修改第 3 節原則 2 的文字**，見 §9。
   - 原則 3（圈內優先）：只能對已交換過金鑰、已被你固定（pinned）的聯絡人開啟，不提供搜尋或推薦。
3. **非目標**：不碰「陌生人社交」——陌生人只能單向寄紙條。
4. **推動指標**：輔助指標「首次紙條互動」與「回覆時間」。

## 1. 意圖

使用者的情境：辦公室同事分兩種——上班時間聊八卦、下班後就不認識的人；以及下班後仍會約出去、繼續聊的人。前者只需要「附近」模式（同一個辦公室網路時能聊，離開就自然斷，伺服器完全不知道你們認識）；後者要能**跨網路延續**：看到對方在線（綠點），聊天像現在直連一樣即時。降級時要**悄悄**進行，對方不會知道。

## 2. 三層模型（使用者核可）

| 層級 | 誰 | 能做什麼 | 伺服器知道什麼 |
|---|---|---|---|
| 陌生人 | 任何知道你 ID／暱稱的人 | 單向寄紙條，**你自己決定要不要打開**，寄件人不會知道你看了沒 | 寄信當下知道寄給誰（現況，不變） |
| 附近 | 同 Wi-Fi／藍牙的人 | 即時聊天，離開範圍就斷 | 什麼都不知道（現況，不變） |
| 一直連線 | 你逐一選的少數朋友，**且對方也選了你** | 綠點、跨網路即時聊天 | 只看到雙方事先約好的暗號；見 §6.1 殘餘風險 |

## 3. 目標、非目標、反目標

### 目標
1. 對已固定的聯絡人，提供**逐人**的「一直連線」開關（預設關）。雙方都開、App 都開著時，出現綠點並自動建立跨網路的加密即時連線。
2. **悄悄降級**：關掉開關後，對方沒有任何通知，也看不出和「你離線」的差別。
3. 對方 App 沒開時，聊天自動退成紙條（專案 C 已具備），不新增推播關聯。
4. 修好現有中繼聊天的既有錯誤，使它能成為日常功能。
5. 陌生人匣：把非朋友的紙條與朋友的紙條分開，預設不推播（產品目標 §4.2 既定，尚未實作）。

### 非目標（第一版）
- iOS 背景常駐連線（PushKit/VoIP 喚醒）：iOS 不允許；綠點＝**對方現在開著 App**。
- 推播「喚醒對方並自動加入房間」：會讓伺服器多知道朋友關係，不做。
- 假房間／假流量（cover traffic）：成本高，使用者接受殘餘風險而不做。
- 多裝置同一帳號合併（一台裝置一個金鑰）。
- 群組即時通話、檔案傳輸以外的新功能（沿用既有訊息協定，檔案／語音是否可用於跨網路連線另行評估）。

### 反目標（做出來卻算失敗，皆為我的推測）
- 伺服器能從資料庫直接讀出「誰是誰的朋友」。
- 降級後對方能看出差異（例如你的綠點「消失」的方式與離線不同）。
- 同一位朋友同時有「附近」與「跨網路」兩條連線而互相打架。
- 背景自動連線干擾前景 UI（現有中繼使用全域狀態）。
- 使用者以為對方在線，其實送出就失敗（綠點與可傳訊息必須一致）。

## 4. 設計

### 4.1 碰面代號（匿名配對）
- 兩人各自以**靜態 X25519 DH**（`IdentityKeyManager.deriveSharedSecret`，與 `LocalSecureChannel` 同一組金鑰）算出共享秘密；再用 HKDF（**獨立的 salt／info**，例如 `"peerdrop-rv-v1"`，與 `PeerDrop-LocalE2E-v1` 不同）衍生**碰面代號**：
  `token = HKDF(DH, salt: "peerdrop-rv-v1", info: min(pubA,pubB) ‖ max(pubA,pubB) ‖ epoch)`，輸出 32 bytes，以 base64url 編碼。
- `epoch` ＝ UTC 日期（天）；兩端都在**日界前後 10 分鐘**同時加入「今天」與「相鄰那天」的代號，避免跨日錯過。時鐘偏差容忍 ±10 分鐘。
- 伺服器知道兩人的公鑰（目錄），但**算不出 DH**，所以無法預先列出代號；每天換新，無法跨日串連。
- 對方的金鑰變更（重裝）時，代號自動不同，不需另外清理；`TrustedContact` 需先處理金鑰變更警示（既有流程）。

### 4.2 碰面房間（伺服器）
- 新增路由 `GET /rv/:token`（WebSocket）：使用**新的 Durable Object 類別 `RendezvousRoom`**（**不重用 `SignalingRoom`**：後者在房間滿 2 人時會把建立超過 60 秒的 socket 當殭屍踢掉，任一方換 clientId 重連就會踢走已在線的朋友）。代號放在**第一個訊框**而非 URL 路徑，避免出現在邊緣／存取日誌；設定 `setWebSocketAutoResponse` 做 keepalive，不讓每個 ping 喚醒 DO 計費；房間維持到雙方都離開或 App 回報離開，另設較長的伺服器端閒置上限（例如 2 小時）。**不預先在 KV 登記**；代號本身就是持有證明（256-bit 隨機性）。
- **不帶 Bearer／裝置 ID**：這條路由使用**匿名**驗證——每次連線附帶一個**輕量工作量證明**（綁定代號＋當前小時；沿用既有 `verifyPoW`/`ProofOfWork` 原語）。速率限制**不只依 IP**（行動網路 CGNAT 下會誤擋，且被擋住的結果與「對方離線」無法區分）：以 (IP, 代號雜湊) 為鍵並給較寬鬆上限；**限流器不得每個請求都寫 KV**（免費方案每日寫入上限會被打爆），改用 DO 內計數或記憶體計數。**明確承認**：PoW 難度對攻擊者成本極低，濫用的實際上限是 Cloudflare 計費，需另設月度成本告警。**`/rv` 絕不寫入 `wslog` 之類會含代號的日誌。**
- 房間行為：兩個 socket 都在時互相轉送訊框；任一方離開通知另一方；**不儲存任何訊息**；閒置 socket 靠休眠 API 不計費；超過 N 分鐘無活動即關閉。
- 營運者可見：連線的 IP、代號（不透明）、時間；**不可見**：deviceId、accountId、朋友關係、內容。

### 4.3 在線（綠點）與連線建立
- 開啟「一直連線」的聯絡人，在 App 進入前景時：對每位開啟者（**最多 5 位**）計算代號並連到 `/rv/:token`；App 進入背景或使用者關閉開關時離開。
- 雙方都在房間時（收到 `peer-joined`）：進行 WebRTC 協商。
  - **信令加密**：SDP／ICE 以雙方的 pairwise 金鑰（由同一 DH 另行衍生，domain-separated）加密並 MAC 後才經房間轉送，伺服器與營運者看不到 IP、DTLS 指紋，也無法中間人。
  - **身分驗證**：建立資料通道後，走既有 `LocalSecureChannel`；握手公鑰必須等於 `TrustedContact` 釘選公鑰，**不再需要 4 位數 PIN**（DTLS 指紋 PIN 只在手動中繼流程保留）。
- 綠點＝`PresenceSources.connected` 含該朋友的跨網路 `PeerConnection`（而不是直接把「伺服器說在線」塞進 `server` 集合——見 §4.7）。
- **悄悄降級**：關掉開關＝不再加入該代號房間（也不再為他進行信令）。對方只看到房間裡沒有人，與「你離線」不可區分；你這邊也看不到他的綠點（在線需要雙方同時在房間）。
- **沒有「對方是否已開啟」的任何訊號**：UI 文案寫「對方也開啟並在線時才會顯示綠點」。

### 4.4 連線管理（修改既有中繼）
- 用**穩定的每人識別**（聯絡人 ID／固定身分 UUID）當連線鍵，不再用 `relay-<房間碼>`；這同時修好現有的「收發對話串分裂」。
- 新的連線類型 `rendezvous`（區別於手動房間碼的 `relay`）：**不受 15 分鐘 TTL 約束**、可同時多個、**不使用全域 `activeRelaySession`／`connectionGeneration`／`forceTransitionToRequesting`**（背景自動連線不能搶前景 UI 的狀態）。
- 同一位朋友同時有「附近」直連與「跨網路」連線時：**偏好直連**；跨網路連線在直連成立後關閉；去重規則放在 `isPeerIDInUse` 周邊並加測試。
- `maxConnections = 5` 目前包含所有連線：跨網路連線佔用名額，需重新定義（跨網路連線單獨計數，與「一直連線」上限 5 位一致）。
- App 進入背景：關閉跨網路連線（沿用背景到期處理）；進入前景：重新加入房間。重連：房間重新加入＋重新協商（需補上 ICE restart 或乾脆重建）。
- Mac：不會被暫停，可長時間維持（仍遵守 5 位上限）。

### 4.5 既有中繼聊天錯誤（必修）
依對照表 §5.4、§1.8，下列為已知問題，須在 E 之前或同時修好並加回歸測試：
1. `sendTextMessage` 用別名查連線，卻用無別名的 `isPeerTrustedForUserActions` 做信任檢查，對由 `ConnectionView` 打開的中繼對象送出會失敗。
2. 收到的訊息存在 `relay-<碼>`，送出的存在身分 UUID，對話串分裂（§4.4 的穩定鍵一併解決，但既有資料遷移要評估：**不做遷移，只讓新訊息用穩定鍵**，舊的 `relay-` 聊天檔保留可讀）。
3. 邀請接受端的 PIN 畫面只在 `RelayConnectView` 顯示（疑似卡住；需實機確認，此為手動流程，若與 E 無關則記錄為既有問題）。
4. `deviceIdExchange` 在 PIN 確認前是 no-op。

### 4.6 陌生人匣（第二個工作流，獨立於 §4.1–4.5；依建置者檢查縮小範圍）
- 紙條分成「圈內」（已綁定的朋友，專案 C 的 `verifiedAccount`；另依產品目標 §4.2 納入同一本日記的成員）與「陌生人匣」（其餘：匿名、未驗證、未綁定）。判斷**只在本機**進行。
- **現實限制**：伺服器對每張紙條都發送可見的推播（`NOTE_RECEIVED`），而伺服器**不知道**誰是陌生人（也不該知道）；專案也沒有 Notification Service Extension。要做到「只對陌生人不推播」只剩：讓伺服器知道關係（違反原則 1）、靜默推播加本機通知（Apple 會節流、不可靠）、或新增 NSE 並申請 `usernotifications.filtering` 權限（需 Apple 核准）。**第一版改為**：新增**全域**設定「紙條通知」（伺服器只存每帳號一個布林值，不涉及關係）；陌生人匣在 App 內以分區與未讀提示呈現。**對陌生人單獨不推播列為後續（需 NSE 權限）**。
- 「不接收匿名紙條」：伺服器**無法**執行（是否匿名只在加密信封內可見）。第一版**只在收件端本機**把匿名紙條收進陌生人匣的「已隱藏」分區或直接丟棄；**不新增伺服器旗標**。
- 寄件人不會知道你看了沒（沿用不做已讀回執）。
- 與專案 C 的關係：已綁定朋友的紙條已經從信箱去重（C 的行為）；陌生人匣是信箱的另一個分區，不改資料格式。

### 4.7 在線狀態整合（與專案 C 的接縫）
- **不使用** `PresenceSources.server` 來直接宣告「對方在線」：現在 `ThreadTransport.decide` 在「在線」時選擇即時聊天，而 `sendTextMessage` 在沒有 `PeerConnection` 時會**靜默失敗**。因此「跨網路在線」必須以**實際存在的 `PeerConnection`** 為準（`connected`），房間裡等待、尚未連上時顯示為「連線中」而不是在線。
- 綠點只代表「有一條已通過身分驗證的跨網路連線」。

## 5. 約束

- 不改既有儲存格式；新增：`TrustedContact` 的一個可選欄位（逐人開關，`decodeIfPresent`）、一條匿名路由、一種連線類型。
- 動伺服器（Cloudflare Worker）：新路由 `/rv/:token`、新的 Durable Object 類別、新的速率機制、匿名的 TURN 憑證路由（見下）、（陌生人匣的）每帳號一個「紙條通知」布林值與 D1 migration。**注意**：`.github/workflows/worker-deploy.yml` 會在 `main` 上 `cloudflare-worker/**` 有變更時**自動**執行 `d1 migrations apply --remote` 與 `wrangler deploy`——所以 worker 的 PR **一合併就是正式部署**，不是獨立步驟。處理方式：伺服器變更先上線且保持**惰性**（沒有任何客戶端使用），客戶端之後才啟用；並在 PR 說明標明。線上 Worker 與 repo 是否同步需先查證。
- **匿名 TURN**：現有 TURN 憑證只能從需登入的 `POST /room/:code/ice` 取得（帶 deviceId，匿名會破功）。新增 `POST /rv/:token/ice`，同樣以 PoW＋速率限制保護；只用 STUN 在行動網路／對稱 NAT 下會有相當比例連不上、綠點永遠不亮。TURN 流量成本需接受。
- 不用新的 App 權限；背景模式維持現狀（不新增 PushKit）。
- iOS 16／macOS 14；`PeerDropKit` 內 UIKit 守衛檢查（CI）需通過。
- 協定相容：舊版 App 不會有此連線類型，也不會連到 `/rv/…`；新版對舊版只在「雙方都有金鑰且都開啟」時才加入房間，且只有擁有同一 DH 的人才會進同一個房間，舊版不受影響。HELLO 旗標不需新增（連線以身分金鑰驗證）。
- 隱私：任何新的日誌不得記錄代號、IP 或朋友關係；錯誤回報不得帶代號。

## 6. 風險與使用者已接受的取捨

### 6.1 營運者能看到什麼（威脅模型，已依建置者檢查更正）
**防得住的**：資料庫被讀取、被調閱或外洩時，**沒有任何儲存下來的朋友關係**；內容端對端加密；代號是不透明的、每天換、算不出來；沒有人能事先列出「誰是誰的朋友」。
**防不住的（誠實說明）**：App 進入前景時，加入碰面房間的連線，與其他已登入身分的連線（紙條同步帶 accountId、收件匣連線的路徑帶 deviceId）會從**同一個 IP、幾乎同一時間**送出。因此**一個有意願做「即時日誌關聯」的營運者（含 Cloudflare）**能把「兩個 IP 在同一時間進同一個代號」對回兩個帳號，推得兩人有往來。這**不是**可用 0–30 秒延遲解決的；要消除只能讓所有人持續連假房間或把兩類流量分到不同出口（iOS 做不到），成本與複雜度過高，**不做**。
**使用者需要確認的取捨**：我們防的是「資料庫與日後調閱」，而不是「擁有即時日誌的營運者」。與主流即時通訊軟體的實務相同。**必須確保營運端不記錄這些關聯**（見 §5 隱私條款）。
**跨日串連**：代號每日輪替，但日界前後雙代號、跨日長連線、固定家用 IP 本身都能串連兩天；視為同一個殘餘風險。
### 6.2 其他
- 對方會看到你的公開 IP（ICE host／srflx 候選）：對象是你主動開啟的朋友，視為可接受；提供「只走 TURN」選項**不在第一版**。
- TURN 使用時 Cloudflare 看得到雙方 IP 與流量大小（既有行為）。
- 首次連線（TOFU）仍可能遇到中間人，沿用現有信任模型。
- 時鐘偏差造成代號不一致：±10 分鐘容忍，超過則看不到彼此。
- 一台裝置一個金鑰：iPhone 與 Mac 是兩位朋友。

## 7. 驗證
- 單元：代號衍生（兩端相同、日期輪替、金鑰變更後不同、domain separation 與 LocalSecureChannel 不同）、日界雙代號邏輯、信令加密／MAC 與竄改拒絕、連線去重規則、`TrustedContact` 新欄位相容、陌生人匣歸類純函式與推播抑制、既有中繼聊天錯誤的回歸測試。
- 伺服器：Worker 單元測試（`/rv` 驗證、PoW、速率桶、2 人上限、閒置關閉）、確認**不記錄**代號與 IP。
- 整合：獨立程序測試（CLI 對等端或測試驅動）完成「兩端開啟→碰面→協商→通道→傳訊」；降級後的不可區分性；舊版 App 相容。
- 實機（使用者）：兩台裝置不同網路的真實連線、前景／背景切換、日界、網路切換重連、Mac 長時間。

## 8. 專案分段（建議）
E1 修既有中繼聊天錯誤與穩定連線鍵 → E2 碰面代號與房間（伺服器＋客戶端信令加密）→ E3 逐人開關與在線／綠點整合 → E4 陌生人匣（獨立，可平行）。

## 9. 與產品目標的差異（待使用者核可）
- §3 原則 2「預設不做…在線狀態」：本專案提供**逐人、雙方同意、預設關**的在線狀態。建議修改措辭為「預設不做在線狀態；只在雙方逐人同意時提供」，並加變更紀錄。
- §4.2 陌生人匣：本專案實作之。

## 10. 我的判斷（請核可時檢查）
1. 一直連線上限 5 位。
2. 降級後你也看不到對方的綠點（在線需要雙方同時在房間）。
3. 沒有任何「對方是否已開啟」的訊號。
4. 對方沒開 App 時不推播喚醒，退成紙條。
5. 碰面代號以 UTC 日為單位，日界前後 10 分鐘雙代號。
6. 房間匿名驗證用 PoW＋速率桶，不用 Bearer。
7. 信令加密，連線以身分金鑰驗證，不用 PIN。
8. 偏好直連；跨網路連線不計入 `maxConnections`。
9. 不遷移舊的 `relay-` 聊天檔。
10. 陌生人匣預設不推播。

## 12. 建置者檢查後的決定（我的判斷，非使用者所說；標「待確認」者請核可時特別看）

1. **誰可以開「一直連線」**：必須是**已綁定帳號（`verifiedAccount`）**的聯絡人，且握手公鑰已釘選。理由：目標 3「對方沒開 App 時自動退成紙條」要求有綁定；也避免 TOFU 階段被換掉的金鑰變成長期自動連線的對象。
2. **前向保密（待確認）**：代號用長期金鑰的靜態 DH 衍生（無狀態，不會不同步）。**代價**：日後任一方私鑰外洩，可回溯算出過去所有日的代號。金鑰存放於 `AfterFirstUnlockThisDeviceOnly`，且營運者必須同時有歷史日誌才能利用；第一版接受。若要前向保密，可改成「首次在通道內交換種子，存入 `TrustedContact`，每日雜湊棘輪並刪除舊值」，代價是有狀態與換機處理。
3. **IP 暴露給朋友**：朋友可以掛一個長期對等端待在房間，記錄你每次開 App 的即時 IP 與作息。**緩解**：悄悄降級後你不再加入該代號，對方看不到你；「只走 TURN」選項列為後續。
4. **悄悄降級的旁路**：無法完全消除——降級後你仍在用 App（寄紙條、日記互動），長期推斷「從不上線卻很活躍」仍可能；連線中途關掉開關時對方看到連線斷了。**接受**。**不提供**「我已開啟」的加密提示（那會讓降級可被察覺）；代價是使用者可能困惑為何沒有綠點，UI 文案寫明「對方也開啟並在線時才會顯示綠點」。
5. **連線完全不退回明文**：`rendezvous` 連線若 5 秒內未建立安全通道就**直接斷線**，不進入 `.fallbackPlaintext`；綠點只在 `secureChannelState == .secured` 且**握手公鑰**（不是 HELLO 宣稱的公鑰）等於釘選公鑰時才亮。信任判斷用握手公鑰。信令加密的作用是防營運者看 IP 與指紋，不是身分驗證；被重放的舊 offer 最多造成連不上。
6. **在線狀態新增一態「連線中」**：房間內只有自己、或正在協商時顯示為「連線中」，不歸入「附近」（避免跨網路朋友被標成「附近」）。`PeerPresence` 需擴充，並檢查所有使用處與測試。
7. **穩定的每人識別（交給計畫階段）**：連線鍵必須與 `FriendBinding` 解析一致；不得與「附近」直連的鍵互相覆蓋（`addConnection` 會覆蓋同鍵連線）；對話串與在線判斷都以同一個鍵。計畫階段須先定出這個鍵與 `DeviceRecord`／`TrustedContact` 的對應。
8. **自動連線不得動到前景 UI 狀態**：不呼叫 `focusedPeerID`／`focusIfUnfocused`／全域 `state` 轉換，不跳出 TOFU／SAS／金鑰變更對話框（遇到需要使用者決定的情況就**不連線**並標示原因）。
9. **專案 C 的交換閘門**不需改：`notesExchangeIsLocalDirect` 會拒絕 `DataChannelTransport`，自然擋下新連線類型。
10. **既有問題（§4.5）先修**。
11. **線上環境（已查，無法確認方案）**：本機 wrangler 登入已過期、GitHub 上的部署金鑰無法讀取，故**無法確認 Workers 是免費或付費方案，也無法確認後台是否開啟 Workers Logs／Logpush／Analytics**（`wrangler.toml` 沒有 `[observability]`；該功能預設需手動開啟）。因此本專案的伺服器部分**設計為不依賴方案**：新路由完全不做 KV 寫入（計數用 DO 內記憶體）、使用休眠 API 與自動回應、代號放在第一個訊框而非網址、不寫任何含代號的日誌；並建議使用者在 Cloudflare 後台設定月度用量告警。自動部署管線已於 2026-07-05 修復（見記憶：PR #128），worker 變更合併後會自動部署，仍須在每次合併後以 `gh run list --workflow=worker-deploy.yml` 確認部署成功。
12. **連線鍵（已定）**：跨網路連線的 `PeerConnection` 以 **`TrustedContact.deviceId`（＝對方的 `PeerIdentity.id`，專案 C 綁定時已保證填入）** 為鍵，並預先帶入身分，HELLO 到達後比對其公鑰須等於釘選公鑰；與「附近」直連使用同一個鍵，因此天然去重（已有直連就不建立跨網路連線；直連之後成立則關閉跨網路連線）。
